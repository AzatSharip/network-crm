# Развёртывание

Compose изолирует проект `network-crm`: PostgreSQL в internal network, API без host ports, nginx только `127.0.0.1:8080`. Реальные данные в named volume вне Git; секреты в отдельном env-файле вне checkout (600). Не запускать общий prune и не менять чужие сети/volumes.

1. Создайте два разных длинных URL-safe пароля, перенесите имена переменных из `.env.example` в защищённый внешний файл. Укажите точный APP_ORIGIN. Для локальной проверки `http://localhost:8080`; для публичного доступа — согласованный `https://...`.
2. `docker compose --env-file /защищённый/путь/network-crm.env up -d --build` (или `docker-compose`, если plugin недоступен). Миграции запускаются отдельным one-shot сервисом перед API.
3. `docker compose --env-file /защищённый/путь/network-crm.env exec api python -m app.cli bootstrap --email you@example.com --name 'Ваше имя'`. Пароль вводится интерактивно, не через аргументы. Bootstrap закрывается после первого пользователя.
4. Откройте локальный адрес, проверьте вход, Personal/Family, создание/поиск/редактирование, приглашение, запрет viewer и чужого Personal.
5. До интернета: согласуйте домен/DNS/маршрут; выпустите доверенный сертификат через существующий механизм с auto-renew; проверьте `nginx -t`, TLS/redirect, Secure cookies, CSRF, отсутствие публичных API/DB ports и конфликта существующих vhosts. Только затем включайте новый vhost. `deploy/https.conf.example` — шаблон, не готовый действующий домен. HSTS включайте после проверки стабильности HTTPS.
6. Настройте и проверьте шифрованные бэкапы (BACKUP_RESTORE.md). Для небольшой закрытой семьи MVP использует случайный длинный пароль, rate limits и серверные сессии. MFA пока отсутствует; для расширения круга пользователей рекомендуется добавить WebAuthn/TOTP или внешний identity-aware proxy.

Тестовый override `deploy/compose.test.yaml` публикует PostgreSQL только на loopback 18432 и использует PostgreSQL 18.7 для локальной разработки. Его нельзя применять к публичному размещению. Production target — PostgreSQL 18.7. Scripts local-env.py предназначен для этой рабочей станции; в CI/других окружениях задавайте DATABASE_URL/MIGRATION_DATABASE_URL явно. Runtime crm_app и migration crm_migrator разделены. Migration role имеет административные права только внутри выделенного PostgreSQL контейнера.

Обновление: backup + restore-check → записать текущий image digest и revision → собрать новый образ → применить миграцию → проверить CRM health и smoke → при ошибке оставить прежние образы/копию для согласованного отката. Не удалять прежний volume. Обновления PostgreSQL major требуют отдельного плана.

Atlas: первоначально только read-only audit ресурсов, портов, проектов, сети/volumes, reverse proxy, TLS и firewall. Конкретные адреса/доступы не должны попадать в публичную документацию. Итог live-аудита и фактическое размещение будут отмечены в PROGRESS/VALIDATION, а чувствительные детали — во внешнем приватном журнале.

## Изолированное подключение к существующему gateway

`deploy/compose.atlas.yaml` добавляет отдельный Unix socket frontend; каталог задаётся CRM_SOCKET_DIR, должен существовать заранее, UID/GID101,0750. Frontend имеет RW mount только этого собственного каталога; API и БД не получают доступ к нему. Socket создаётся с umask007. HTTP host port остаётся loopback для приватного smoke.

`existing-gateway-vhost.conf.in` — добавочный TLS server block, не замена действующего proxy. Его применение к общей точке входа требует проверки точного diff, существующих маршрутов, nginx -t и разрешения владельца до изменения live-конфигурации. Параметры hostname/certificate/socket заполняются в приватном deployment-пакете. Не менять действующий listener, сети, firewall или чужие upstream. Сначала отдельный backup существующего config, после reload — проверки старых сервисов и откат только нового изменения при регрессии.

DuckDNS: `duckdns-cert-hook.py` работает только с TXT через документированный TXT API. Приватный root0600 JSON содержит hostname, parent, credential_file; credential file также root0600 и содержит domain/token. Hook допускает только один вложенный hostname данного parent, проверяет CERTBOT_DOMAIN и не пишет A/AAAA. TXT общий для всех sub-subdomains: использовать штатный Certbot global lock, не запускать параллельные ACME-клиенты. Cleanup не очищает несовпадающий challenge. Существующие hooks/сертификаты не заменяются. `cert-deploy.py` проверяет доверие, hostname, срок и соответствие ключа, публикует только отдельную пару файлов UID101 и откатывает их при ошибке nginx -t/reload. Приватный root0600 JSON содержит hostname/lineage/target/container/reload. На этапе staging reload=false; включить только после согласования gateway. Проверить certbot renew --cert-name выбранное-имя --dry-run; без проверки auto-renew настройка не завершена.

На текущем Atlas стандартный внешний 443 обслуживается другой системой; согласованный дополнительный ingress использует 8443. Шаблон перенаправляет обычный HTTP на этом порту в HTTPS (nginx497). Порт80/стандартный443 не перенастраиваются. Для file bind mount nginx.conf нельзя полагаться на atomic rename: контейнер сохранит старый inode. Применять проверенный diff в существующий inode с fsync, сохранив root0600 backup и контрольную сумму; nginx -t перед graceful reload. При любой ошибке восстановить прежние байты, проверить и перечитать конфигурацию.

Пакет исходников с macOS создавайте без AppleDouble/xattrs (COPYFILE_DISABLE=1 tar --no-xattrs); Docker context также исключает ._* и .DS_Store. На текущем Colima сборка выполнялась в гостевой файловой системе из-за зависающих host bind mounts.
